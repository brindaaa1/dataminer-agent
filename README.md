# DataMiner Agent

上传一张表和一段业务说明，DataMiner Agent 会先和你确认建模口径，再逐轮做特征、比较模型、调参，最后交给你一份报告和一个可以下载的模型。目前只处理二分类。

它想替代的是一位数据分析师完成一次建模的过程，不追求在某个数据集上刷出最高分。LLM 在这里负责提出下一步做什么、为什么；训练、指标计算、实验是否被采纳，全部由代码判定。整个设计都建立在这条分工上：LLM 可以提建议，但不能给自己判卷。

## 快速开始

```bash
git clone -b feature/agent-eval-workbench https://github.com/brindaaa1/dataminer-agent && cd dataminer-agent
./start.sh
```

`start.sh` 会安装 Python 依赖，第一次运行（或前端有改动）时构建前端，然后启动服务并打开 http://127.0.0.1:8000 。需要 Python 3.10 及以上（在 3.12 上测试）和 Node.js。不想用脚本也可以手动执行：

```bash
pip install -r requirements.txt
cd web && npm install && npm run build && cd ..
uvicorn server.app:app --port 8000
```

不需要账号、数据或 API key。想用真实模型，把 `.env.example` 复制成 `.env`，填上 DeepSeek、Kimi 或 Anthropic 的 key。

打开后是工作台：

- **示例**：左侧"示例"是此前真实调用 LLM 的运行记录，只读，不需要 key。三个示例都是从工作台完整跑下来的：上传数据和业务说明、接入对话、建模、报告。
  - `elec_deepseek`：澳大利亚 NSW 电价涨跌（Elec2），最终检验 AUC 0.928。
  - `hotel_deepseek`：酒店预订是否取消，最终检验 AUC 0.839。
  - `lc_deepseek`：Lending Club 贷款是否违约（信贷风控），最终检验 AUC 0.667。原始数据不随仓库分发。
- **新建任务**：自己走一遍。`data_sample/electricity/` 下有电价数据和一份业务说明，上传这两样即可。没有 key 时 LLM 选 mock，接入阶段直接给出一次 DeepSeek 确认过的配置，建模部分照常运行，一分钟左右出报告。
- 右上角的"开发者视图"打开后，能看到 LLM 原文（Trace）、评测结果、诊断码和完整模型卡；默认只显示业务人员需要的内容。

示例的完整 trace 也可以在 Langfuse 上查看（公开，无需登录），产出页的"查看详细分析过程"也会跳到这里：

## 数据约定

agent 能处理的数据需要满足以下几点。满足的数据不需要改代码；不满足的情况见"已知边界"。

| 项 | 要求 |
|---|---|
| 格式 | 一个 CSV，一行是一个要预测的对象（一笔订单、一笔贷款、一个半小时时段……） |
| 标签 | 有一列（或能由某列推出）二分类结果，比如是否取消、是否违约、涨还是跌 |
| 时间 | 最好有一个时间列。有时间列时按时间切分，用最近的一段单独检验；没有时只能随机切分，看不出模型放到未来是否稳定 |
| 业务说明 | 几句话：要预测什么、结果怎么定义、在什么时点做预测、哪些字段事后才有 |

接入时 agent 会起草一份配置，其中四项必须由你确认：标签怎么定义、预测时点、时间切分窗口、评价指标。此外，每个字段会被标上"可得时间"，决定它能不能进模型：

| 可得时间 | 含义 | 处理 |
|---|---|---|
| 预测时已知 | 下单时的渠道、贷款期限等 | 直接使用 |
| 历史值可用 | 当期值预测时未知，但过去各期的值已知，比如上一个时段的电价 | 代码生成滞后值和滑动平均（如 `nsw_price_lag1`、`nsw_price_mean48`），当期值不进模型 |
| 结果之前会更新 / 结果之后才有 | 订单状态、还款记录等 | 隔离或剔除 |
| 不确定 | 说明里没提、agent 判断不了 | 先隔离，并在追问里请你确认 |

标签的来源列也可以标"历史值可用"。电价的例子里，当前时段的电价就是标签的计算来源，属于泄漏；但过去时段的电价和涨跌在预测时已经知道，是最有用的特征。没有这一类时，Elec2 只剩三个特征，最终检验 AUC 0.759；加上之后是 0.928。

## 工作机制

### 整体流程

```text
接入：数据画像 → LLM 起草配置 → 代码校验 → 追问 → 用户确认 → 写出配置
                                                              ↓
建模：PROFILE → PLAN（模型赛跑）→ DECIDE → EXECUTE → EVALUATE → RECORD → STOP_CHECK
                                    ↑                                       │
                                    └──────────────── 继续 ──────────────────┤
                                                                            ↓
收尾：                                        FINAL_GATE → REPORT → CONSOLIDATE
```

数据切成四段：`train`、`valid`、`oot_dev`（时间外验证，建模中反复使用）、`holdout`（最终检验，只在最后读一次）。

每个状态转换、实验记录和 Optuna study 都写进检查点。进程被中断（包括 `kill -9`）后，从工作台点"续跑"或在命令行重复同一条命令即可接着跑：已完成的实验直接复用，不重新训练。

### 接入：把业务说明变成可执行的配置

代码先计算数据画像（列名、类型、样例值、缺失率、候选的日期列和标签列）。LLM 只看画像和业务说明，不看原始数据行，据此起草：标签、预测时点、切分窗口、每个字段的可得时间、需要剔除或隔离的字段、指标，以及一段给用户看的数据描述和所属领域。

草稿由代码校验：字段必须存在；时间表达式在 DuckDB 中实际执行，非空比例不低于 99%；切分窗口按时间先后排列、互不重叠，每段都有正负样本。出错时把错误回灌给 LLM 重写。四个必答项即使 LLM 给了推荐值也要你确认；之后的草稿如果改动了已确认的内容，会再问一次。

同一结构的数据再次上传时，上次确认过的标签、预测时点、时间窗口直接作为推荐答案；每个领域记住上次用的指标。

### 建模：先赛跑，再逐轮改进

**模型赛跑。** lgbm 和 catboost 一定参加，LLM 根据数据画像和模型档案可以再提名最多两个（随机森林、评分卡）。所有候选在相同特征下抽样快速试跑，按时间外验证的表现比较。几个模型的差距小于这份数据能分辨的最小提升（MDE，由 DeLong 方差算出）时算"效果相当"，按固定偏好（catboost → lgbm → 随机森林 → 评分卡）挑一个，然后直接全量训练，作为第一个正式模型。

**逐轮改进。** 之后每一轮由 LLM 决定做什么：加特征、调参、换模型、查数据，或者停止。可选的动作有：

| 动作 | 说明 |
|---|---|
| 加特征 | 按 `knowhow/` 里的模板生成，模板表达不了的用 `run_code` 写 Python；所有特征都要过缺失率、IV、单特征 AUC、相关性和 PSI 筛选 |
| 调参 | LLM 给方向和范围，Optuna（TPE + 剪枝）在范围里搜索具体数值 |
| 换模型 | 必须写明触发的诊断（过拟合、长期无进展、护栏指标变差等）和目标模型档案中对应的一条 |
| 查数据 | 只读查询训练集的聚合统计：单特征 AUC、信息值、互信息、分箱正类比例、前后两半的稳定性、缺失与目标的关系、冗余特征 |

**生成端放开、验证端收紧。** LLM 可以在模板里自由组合特征、提出新假设，模板表达不了的还能直接写 Python（`run_code`）。但 `run_code` 只能读到预测时点可得的字段，被剔除和隔离的字段对它不可见；它产出的特征和模板特征走同一套筛选，单特征信号过强会按疑似泄漏处理。也就是说，LLM 想法再多，能进模型的只有通过检验的那部分。

**业务先验是待检验的假设，不是默认成立的规则。** 数据集的先验文件（`knowhow/<数据集>/priors.yaml`）可以写某个特征和目标的方向（比如负债收入比越高越容易违约），LLM 可以据此给 lgbm 加单调约束。加之前，代码先检查先验和训练数据是否明显矛盾，矛盾的特征跳过并写进报告；加之后，只有在效果不显著变差、分数稳定性（PSI）确实更好时才保留约束。

新方向先抽样快速试跑。试跑结果比当前最好的高出至少一个 MDE，才值得全量训练；只有全量训练的结果能被采纳。每一轮还会给业务人员写一句说明：这一步做了什么、为什么。

**停止。** 连续几轮没有超过 MDE 的进展、轮数达到上限（默认 6）或预算用完时停止。评测中一次运行通常 4 轮就停。

**为什么最终模型常常是第一个。** 三个示例的最终模型都是赛跑胜者全量训练得到的那个，评测中也一样（升全量 23 次，只采纳 1 次）。这是门槛设计的结果：赛跑胜者升全量时已经调过参，单表数据上通常接近上限；之后的新尝试要比它高出至少一个 MDE 才算真的更好，而加派生特征、微调参数带来的提升往往只有千分之几，和噪声分不开。所以逐轮改进的主要作用是确认没有更好的方案，然后按规则停下；效果的大头来自接入时把口径定对（比如电价的历史值可用）和赛跑选对模型。

### 判定：代码说了算

- **配对比较**：候选模型与当前最好的模型在同一批时间外验证样本上做配对 bootstrap。显著性阈值随比较次数收紧，比较次数有上限，以降低反复试验带来的偶然显著。
- **诊断**：每个实验检查验证集与时间外验证的差距、疑似泄漏（单特征 AUC 过高）、分数漂移、连续无进展。诊断码附带一条策略建议交给 LLM；LLM 选择别的动作时必须写理由，否则校验不通过。
- **LLM 的意见只记录、不采用**：LLM 在输出中夹带的"应该采纳"不参与判定。
- **最终检验**：holdout 只由 `FinalGate` 读一次，读取需要它签发的 token；测试静态检查 `agent/`、`tools/` 下的代码没有导入它、也没有引用 holdout 目录。最终检验比时间外验证低得明显、而默认参照模型（lgbm）没有这么低时，标记为"疑似对时间外验证过拟合"。
- **指标口径先锁定**：主指标（默认 AUC）和护栏指标在任务开始前确定，运行中不能改，避免看到结果后再挑对自己有利的指标。

### 产出

- **报告**：执行摘要、建模过程（每一步做了什么、为什么）、效果（训练集、时间外验证、最终检验，外加头部 10% 的提升度和召回、Brier 分数）、主要特征、风险提示，最后是复现用的模型设定：训练方式、随机种子、每个参数的取值和含义、完整特征清单。这部分由代码按模板生成，不经过 LLM。工作台里可以直接下载。
- **模型**：最终模型文件和特征定义，开发者视图里可以打包下载全部产出。
- **trace**：事件日志和每次 LLM 调用（阶段、耗时、token、prompt 和回复原文）都保存在本地；配了 Langfuse 时同时上报。
- **经验**：运行结束后，LLM 可以提出候选经验，必须引用真实实验；经验的启用和废弃由规则决定。相似的新任务会用历史最优参数热启动。

### 领域知识

业务知识按领域手册组织（`knowhow/domains/`）。通用手册对任何二分类都成立；信贷风控是第一份填好的领域手册，包含常用指标、典型泄漏字段、特征思路；其他领域按 `_template` 补一份即可，不用改代码。数据集自己的字段定义、泄漏黑名单、特征模板放在 `knowhow/<数据集>/`，接入新数据时由 agent 起草生成。

## 评测闭环

agent 的每次改动都要经过同一套评测，而不是靠一两次运行的观感。

1. **固定的评测集**：快档是酒店预订、Lending Club 各 2 个种子，外加 4 个情景用例：埋入泄漏字段、缺少必要配置、时间外样本太少、数据没有信号。全档加上 Home Credit（多表）和第 3 个种子。
2. **基线**：每个数据集都跑 B0（默认参数的 lgbm）和 B1（5 分钟预算的 AutoML），agent 的结果和它们并列比较。
3. **噪声带**：同一份代码跑两次（A/A），两次之间的差异就是噪声。新版本和上一版按种子配对比较，超过噪声带、而且多数种子同向，才算真的变好或变坏。
4. **过程指标**：除了最终效果，还统计轮数、被拒绝的决策、浪费的轮次、试跑升全量的命中率、用时和花费，以及每个情景用例是否按预期处理。
5. **记录**：结果写到 `eval/suite/results/<版本>/`，开发者视图的"评测"页签可以按版本查看和对比；每一版改了什么、看到了什么记在 `docs/eval/JOURNAL.md`。

```bash
caffeinate -i python -m eval.suite.run --label v14 --tier fast --jobs 4      # macOS 上用 caffeinate 防止睡眠中断
```

这套流程实际改掉的问题见文末"版本迭代"。

## 已知边界

- **任务类型**：只做二分类；多分类、回归还没有。
- **多表**：工作台只接收单表。命令行可以跑 Home Credit 这样的多表数据，但跨表关联的配置需要手写。
- **过拟合口径**：过拟合检查看的是主指标"验证集 − 时间外验证"的差值（AUC 阈值 0.03）。这只是示例口径，实际上线还需要分数 PSI、分月指标波动等稳定性指标。季节性强的数据上，这个差值拦下的是"同期验证集分数高"的模型，真正的季节性下滑它识别不出来：酒店数据上，lgbm 两次全量训练被它拒绝，最后通过的评分卡在最终检验上反而下滑更多。改口径会影响所有已有结论，计划单独处理。
- **逐轮改进很少被采纳**：抽样试跑的结果是和已全量训练、调过参的当前最好模型比的，比较本身对新尝试不利；连续几次同向的小幅提升也不会累积起来。可以改成同样的抽样和调参次数下比较，或者允许合并多次小幅提升后升一次全量，需要跑一轮评测确认。
- **`run_code` 不是沙箱**：只用子进程和超时控制，没有容器级隔离，不能用来执行不可信的代码。
- **人工介入**：工作台固定为无人值守；命令行的 L1 模式会在疑似泄漏等情况下暂停，但还不是完整的审批流程。
- **模型范围**：只能在已登记的四种模型里选，不能提出新的模型结构，也不做集成；单调约束只支持 lgbm。
- 现有实验说明流程能跑通、部分设计假设成立，不足以证明在任意数据上都有效。真实业务接入时，标签成熟度、字段可得时间、切分和验收口径仍需要逐项确认。

## 版本迭代与收获

agent 的主要迭代都是按评测结果做的。每一版的完整记录见 `docs/eval/JOURNAL.md`。

| 版本 | 改了什么 | 评测看到的 |
|---|---|---|
| v7a / v7b | 评测上线，第一次 A/A | 同一代码在酒店上差 0.016，赛跑选模型不稳；噪声带改成按数据集分 |
| v8 | 抽样试跑至少保留 2 万行 | 酒店赛跑稳定了，但 Lending Club 每次都跑满 8 轮，用时翻倍 |
| v9a / v9b | 试跑"更好"要超过半个 MDE；LLM 调用加超时 | 轮数降到 4，用时降到原来的三分之一左右 |

几点收获：

- **大部分提升来自"别在噪声里做决定"。** 20 次赛跑里有 18 次几个模型的差距小于 MDE，之前 LLM 在这些噪声差异里挑模型，结果随种子摇摆。打平规则加固定偏好之后，选择稳定了，也省掉了大量没有意义的试跑：试跑升全量做了 23 次，只有 1 次被采纳。
- **用时和效果要一起看。** 偏好 lgbm 时酒店的最终检验低 0.015，所以 catboost 还是放在第一；但它慢，这笔账只有评测表里同时列出用时和花费才算得清。
- **评测也会抓到工程问题。** LLM 调用没有总时长上限，一次规划卡了 36 分钟；Mac 睡眠让一次评测停了几个小时。这些都不是模型问题，但都会被误读成"agent 变慢了"。
- **换一份新数据，暴露的是机制缺口，而不是参数问题。** Elec2 暴露了"可得时间按整列判断"这个口径太粗。补上"历史值可用"之后，同样的代码不用为这份数据做任何特殊处理。之后接入新数据，应该先看它在数据约定之内还是之外，而不是逐个数据集调参。
