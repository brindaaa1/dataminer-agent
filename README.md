# DataMiner Agent

DataMiner Agent 面向表格数据的自动建模：给定一张表和建模目标，agent 逐轮完成特征构造、模型比较和调参。LLM 负责提出下一步做什么以及理由；训练、指标计算和实验是否被接受，全部由代码判定。这条分工是整个设计的出发点：LLM 可以提建议，但不能决定结论。

主要场景是信贷风控，使用 Lending Club（单表）和 Home Credit（多表）数据；另配有酒店预订取消预测，用于检验同一套流程能否迁移到其他业务。项目目前仍是研究原型。接入新数据集时，字段定义、标签口径和时间规则可以由 agent 根据数据和业务说明起草、经人确认后使用；特征模板仍需手写。

## 快速开始

```bash
git clone -b feature/flexible-modeling https://github.com/brindaaa1/dataminer-agent && cd dataminer-agent
pip install -r requirements.txt
streamlit run app.py
```

需要 Python 3.10 及以上（在 3.12 上测试）。不需要账号、数据或 API key。页面顶部是仓库自带的酒店预订样本，下方有三个标签页：

- **历史回放**：按原顺序重放此前真实调用 LLM 的运行记录，不是实时运行。默认是 DeepSeek 在酒店样本上的一次运行。每一轮的假设、理由、结果和代码判定以卡片展示；卡片上方是各轮指标图，卡片下方可以展开这一轮的调参过程。另外三次是 Kimi 在 Lending Club 全量数据上的早期运行，原始数据不在仓库中。
- **现场运行**：在样本上从头完整运行一次，页面随进度更新。默认使用按固定策略决策的 mock LLM，约十秒完成；也可以填入自己的 DeepSeek、Anthropic 或 Kimi key。key 只在当前页面会话中使用，不写入磁盘，也不记录到日志。
- **接入新数据**：回放一次真实的接入会话，即 agent 根据数据画像和业务说明起草配置、追问必答项、代码校验后写出配置的过程，并与手写配置对比。回放结束后可以用生成的配置当场运行一次建模。填入 key 后也可以上传自己的数据。

- **许可**：酒店数据随同行评审的数据论文以 CC BY 4.0 发布，署名并注明改动即可再分发。Lending Club 和 Home Credit 均来自 Kaggle，再分发条款未确认允许。

- **配置现成**：酒店数据的字段定义、泄漏字段标注和切分窗口已在 `knowhow/` 中配置好，泄漏检查消融实验也使用这份数据。

代价是演示展示的是跨场景迁移，而不是信贷主场景。信贷场景的运行可以在"历史回放"中查看 Lending Club 的三次 Kimi 运行，完整结果见 `examples/`。

## 设计思路

这个项目想回答的问题是：在奖励明确、可以被验证的任务里（这里是 OOT AUC），怎样让 LLM 参与数据挖掘，又不让它给自己判卷。做法是把工作拆开，LLM 负责发散和决策，确定性代码负责执行和验证。

希望 agent 覆盖四类能力，对应的做法和完成程度如下：

| 要求 | 做法 | 主要代码 |
|---|---|---|
| 自己设计和选择模型 | LLM 依据模型档案和数据画像提名候选，候选在相同特征和预算下抽样试跑，由 OOT-dev 表现和配对比较决定从哪个模型继续；之后由诊断信号提示换模型。LLM 也可以把业务先验变成单调约束，约束是否保留由对照实验决定。详见"改进"中的模型选择。 | `modeling/zoo.py`、`modeling/monotone.py`、`agent/actions.py` |
| 用 know-how 设计特征 | 字段语义、泄漏黑名单和特征模板写在 `knowhow/`。模板按实体、时间窗口、聚合方式和派生方式组织，代码按 point-in-time 规则展开成 SQL，再经过筛选。模板表达不了的想法走 `run_code`。多级聚合和跨表关联模板还没有做全。 | `knowhow/`、`features/`、`tools/run_code.py` |
| 基于 AUC 逐步调参 | 分两层：LLM 每轮决定调什么、往哪个方向、范围多大，Optuna（TPE 与剪枝）在范围内找具体数值。先抽样试跑，结果可观再全量复验；每一步都用 OOT-dev 主指标（默认 AUC）的配对 bootstrap 判定。 | `agent/decide.py`、`modeling/inner_loop.py`、`evaluation/compare.py` |
| 自行处理过拟合等边缘情况 | 每轮自动诊断验证集与 OOT-dev 的差距、疑似泄漏、分数漂移和连续无进展，诊断码映射为策略先验交给 LLM；OOT-dev 的比较次数有预算，显著性阈值逐步收紧；holdout 只在最后读一次。当前口径的局限见后文"关于 OVERFIT_GAP 的口径"。 | `evaluation/`、`data/access.py` |

几条贯穿始终的原则：

生成端放开、验证端收紧。LLM 可以在 know-how 词表里自由组合特征、提出新假设，甚至通过 `run_code` 直接写 Python，但所有产出都要经过同一套筛选；`run_code` 的特征默认视为可疑，需要人工确认。

判定权只在代码手里。实验能否被接受只看 evaluator 的结果，LLM 在输出里夹带的判断会被记录，但不会被采用。LLM 偏离诊断给出的策略先验时，必须写出理由，否则校验不通过。

Holdout 在代码层面就拿不到。读取需要 `final_gate` 签发的 token，其他模块无法获得；测试会静态检查 `agent/` 和 `tools/` 下的代码，确认它们没有导入 `final_gate`，也没有引用 holdout 目录。

经验只能由 LLM 提出、由规则批准。候选经验必须引用真实实验，键名来自代码从实验树推导出的枚举，晋升和废弃由生命周期规则决定；不相似的任务直接冷启动。

换场景的目标是只换配置、不改代码：新数据集主要补充 `knowhow/` 下的字段定义、标签、时间规则和模板，以及 `config.yaml` 中少量的解析设置。酒店预订这个非金融场景就是用来检验这一点的。

## 改进

### 模型选择

模型库有 lightgbm、评分卡、CatBoost 和随机森林四种，每个模型附一段档案，写明适合什么数据、主要风险是什么。

此前模型赛跑会跑完模型库中的全部模型，LLM 只在赛跑之后参与。模型变多以后，全部赛跑的成本上升，"从哪几个模型开始"也需要依据。现在规划阶段把数据画像（样本量、坏样本率、类别列数、最大基数等）和模型档案交给 LLM，由它提名 2～3 个候选。每个理由必须引用档案中的一条并对上画像中的数字，例如"类别列 12 个、最大基数 178，档案：高基数类别变量多时占优"。候选经约束过滤后进入赛跑，由赛跑结果决定起点。

没进入赛跑的模型只能通过 `SWITCH_MODEL` 进入。推荐换模型的诊断码是 `OVERFIT_GAP`、`PLATEAU`、`GUARD_FAIL` 和 `OOM`，其中 `PLATEAU` 表示调参已没有显著提升，当前模型的归纳偏置难以再挖出信号。LLM 换模型时要写明触发的诊断码，以及目标模型档案中对应的一条。

还没做的：LLM 只能在已登记的模型中选择，不能提出新的模型结构，也不能组合集成或 stacking；单调约束只支持 lightgbm。

### 指标口径

指标分为一个主指标和若干护栏指标。主指标决定所有比较，Optuna 的优化目标、过拟合差值和配对 bootstrap 都用它。护栏指标不参与排名，只负责拦截：候选模型在 OOT-dev 上的护栏指标比当前最优变差超过容差，就判定为拒绝，诊断码为 `GUARD_FAIL`。模型赛跑是同批候选之间的比较，不检查护栏。风控场景的护栏是 KS，其他场景是 PR-AUC；各数据集的主指标目前都是 AUC。

口径在任务开始前锁定，运行中和中断恢复后都不能更改，避免 LLM 看到结果之后再挑对自己有利的指标。每次实验对 train、valid、OOT-dev 三段计算全部指标，模型卡中并列展示。

还没做的：过拟合检查仍只看主指标的"验证集 − OOT-dev"差值，季节性数据上的问题见后文"关于 OVERFIT_GAP 的口径"；指标没有和业务成本挂钩，例如按误拒、误放的代价加权；KS 作为主指标时，lightgbm 和 CatBoost 的早停与剪枝仍以 AUC 近似。

### 建模过程可视化

演示页展示两层循环。外层是 LLM 每轮决定方向、代码判定结果：轮次卡片上方的图中，每个实验一个点，纵轴是 OOT-dev 主指标，被接受的点加粗描边。内层是 Optuna 在 LLM 给定的范围内搜索：每张卡片下方可以展开这一轮的 trial 曲线，包括验证集得分、至今最优和被剪枝的 trial。默认只展开被接受的轮次。图下注明 Optuna 只看验证集，OOT-dev 在搜索结束后才评估一次。历史回放中的四次运行都带有完整的 trial 记录。

还没做的：参数重要性、不同轮次搜索空间的对比、跨运行比较。

### 接入新数据

用户提供一张表和一段业务说明。代码先计算数据画像（列名、DuckDB 类型、样例值、缺失率、候选日期列和标签列），LLM 只看画像，不看原始数据行，据此起草配置：标签、预测时点、切分时间和窗口、每个字段的可得时间、需要剔除和隔离的字段、主指标与护栏。产出的配置与手写格式相同，注册后直接进入现有建模流程。

草稿由代码校验：字段必须存在；时间表达式在 DuckDB 中实际执行，非空比例不低于 99%；标为日期的字段必须能解析成日期；切分窗口按时间先后排列、互不重叠，每段都有正负样本。出错时把错误回灌给 LLM 重写。LLM 写的表达式只能读取这张表，不能访问本机其他文件。

标签、预测时点、切分窗口、指标四项是必答项，LLM 给了推荐值也必须经用户确认。确认时记下当时的值；之后的草稿如果改动了已确认的内容，代码会再次追问。写出的配置中，这四项一律采用确认过的值。其他存疑之处由 LLM 自行追问，每个问题附推荐答案。

演示页回放的是一次真实会话（DeepSeek，酒店样本）。业务说明没有写哪些字段在入住后才产生、哪些会被事后更新，也没有给切分窗口；业务方依据手写配置如实回答，LLM 没问到的不主动透露。会话共三轮草稿：

- 第一轮：LLM 除四个必答项外追问了 `assigned_room_type`。草稿先因把整数年份标为日期被退回，又因输出格式不符被退回，改正后通过。
- 第二轮：用户上一轮改了护栏指标，代码把新值拿回来请用户再次确认。LLM 提出用 `reservation_status_date` 作为切分时间，这是订单结果发生后才有的日期，被业务方否决。另有四个下单后仍会变化的字段，按业务方的回答隔离。
- 第三轮：没有待确认的问题，写出配置。

与手写配置相比，泄漏字段识别出 4 个中的 3 个，存疑字段隔离了 5 个中的 4 个，字段可得时间的判断 31 个中 27 个一致（87.1%）。没识别出来的是 `required_car_parking_spaces`（疑似入住时才登记）、`country`（可得时间存疑）和 `arrival_date_year`（只用于切分），都需要业务经验才能判断。用生成的配置运行一遍建模流程，可以正常完成。

还没做的：接入流程只在酒店数据上演示过；漏掉的字段会进入模型，更可靠的做法是追问阶段对每个字段给出可得时间的依据，让用户批量复核；多表与跨表关联、派生特征和特征模板的自动生成、行过滤与标签成熟度规则、字段合规标注，目前仍需手写。

## 工作流程

系统由状态机驱动。完成任务信息检查和数据分析后，进入"决策 → 执行 → 评估 → 记录"的循环，满足停止条件后进行最终验收、生成报告并沉淀经验。

```text
INTAKE → CLARIFY（按需）→ PROFILE → PLAN
                                    ↓
             DECIDE → EXECUTE → EVALUATE → RECORD → STOP_CHECK
                ↑                                      │
                └────────────── 继续实验 ────────────────┤
                                                       ↓
                                    FINAL_GATE → REPORT → CONSOLIDATE
```

LLM 只参与规划方向、每轮决策、报告叙述和候选经验整理。其输出先经过 Pydantic 和业务规则校验，不符合要求时，系统把错误原因返回给 LLM 并要求重新输出。

数据分为 `train`、`valid`、`oot_dev`、`holdout` 四段。Lending Club 和酒店数据按时间窗口切分；Home Credit 缺少绝对日期，只能分层随机切分，因此其 `oot_dev` 无法验证跨时间稳定性。

## 特征与模型

特征构造从 `knowhow/` 中的字段定义和模板开始。模板描述实体、时间窗口、聚合方式和派生公式，特征工厂将其转换为 SQL 并按配置执行时间过滤。目前支持部分单级聚合和行级派生，多级聚合和跨表关联模板尚未全部实现。

模板无法表达的计算可以通过 `run_code` 提交 Python 代码。所有特征都要经过缺失率、IV、单特征 AUC、相关性和 PSI 筛选，单特征信号过强会触发泄漏告警。`run_code` 产出的特征一律标记为"可得时间待确认"，需要人工确认后才能进入后续流程。

新方向先在部分数据上**抽样试跑**（代码中为 `fidelity: low`，默认抽取 10%），结果可观时再用**全量数据复验**（`fidelity: full`）。只有全量训练的结果可以被接受并成为最终模型。调参由 Optuna 完成（TPE 与剪枝），LLM 负责选择搜索方向、是否切换模型以及搜索范围。

开发中遇到过一个典型问题：DeepSeek 第一次在样本上运行时，五轮都停留在抽样试跑阶段调参，没有产出最终模型。原因有两点。一是样本规模小，抽取 10% 后只剩约四百行，诊断信号基本是噪声，因此样本上的试跑比例改为 50%。二是 LLM 没有意识到"不进行全量复验就不会有最终模型"：Kimi 在 Lending Club 上自行做到了这一点，DeepSeek 没有，这类行为本身具有随机性。为了让结果稳定，代码在"尚无最终模型、但已有可复验的试跑结果"时加入诊断码 `NO_FINAL_MODEL`，其策略先验指向全量复验；LLM 若选择其他动作，必须给出理由。

业务先验也可以转为模型约束，例如为部分特征指定风险的单调方向，再通过对照实验决定是否保留。先验不默认成立，代码会先检查它与训练数据是否明显冲突。

## 评估

每个实验都会检查验证集与 OOT-dev 的指标差距、疑似泄漏、分数漂移、特征数量和连续无进展，诊断结果作为下一轮决策的依据返回给 LLM。

候选模型与当前最优模型在同一批 OOT-dev 样本上做配对 bootstrap 比较。显著性阈值随比较次数收紧，并设有使用次数上限。这一机制用于降低反复试验带来的偶然显著风险，并不代表已经消除对 OOT-dev 的过拟合。LLM 给出的接受或拒绝意见会被记录，但不参与判定。

Holdout 只在最后由 `FinalGate` 读取一次。读取需要验收模块签发的 token，结果按任务记录，正常流程无法重复评估。这属于应用层访问控制，不是操作系统级隔离。

### 关于 OVERFIT_GAP 的口径

当前的过拟合检查使用任务的主指标（各数据集目前都是 AUC）：验证集与 OOT-dev 的主指标之差超过该指标登记的阈值（AUC 为 0.03）即拒绝。这里选择 AUC 仅作为示例，实际上线时只看这一个差值并不充分，还需要纳入稳定性相关指标，例如分数 PSI、分月 AUC 波动、与同期基线的对比等。

酒店数据是一个反例。该数据季节性很强：验证集与训练集属于同一时期，OOT-dev 是随后的冬春季，holdout 是夏季。在样本上，lightgbm 全量训练后的差值为 0.037～0.041，两次均被拒绝。最终通过的是评分卡，但它在 holdout 上从 0.816 降至 0.731，验收将其标记为"疑似对 OOT-dev 过拟合"。全量数据上情况类似：默认 lightgbm 基线的 OOT-dev、holdout AUC 为 0.833 和 0.785，agent 最终保留的评分卡为 0.829 和 0.775，lightgbm 并不逊色。

也就是说，在季节性数据上，这一差值拦下的是"同期验证集分数高"的模型，而真正的季节性下滑它无法识别。调整口径会影响所有数据集和已有实验的结论，计划单独处理，本次没有改动。

## 运行记录与 trace

运行过程中会保存事件日志、实验记录和检查点。进程中断后使用同一条命令即可恢复，已完成的实验直接复用，Optuna study 也会保留。运行结束后生成模型卡和 Mermaid 实验树。

演示页中的"每一轮"由事件日志切分得到：每进入一次 DECIDE 计为新的一轮。每次 LLM 调用都会记录所处阶段、耗时、token 数以及 prompt 和回复原文，报错信息中的 key 片段会被脱敏。

如需更细致的查看，可以接入 [Langfuse](https://langfuse.com)。在 `.env` 中填写 `LANGFUSE_PUBLIC_KEY`、`LANGFUSE_SECRET_KEY` 和 `LANGFUSE_HOST`（格式见 `.env.example`）后，运行时会自动上报：

- 建模运行：trace 名为 `dataminer · <task_id>`，session 为 `<task_id>`。其下依次是准备、各轮和收尾，再往下是各状态、每次 LLM 调用和事件。命令行运行的 task_id 就是 `--task-id`，演示页现场运行为 `live_<LLM 名称>_<月日_时分秒>`，如 `live_mock_0930_153012`。
- 接入会话：trace 名为 `dataminer · intake · <数据集 id>`，session 为 `intake_<数据集 id>`。其下依次是数据画像、各轮起草（LLM 调用、校验失败、追问、用户回答）、写出的配置和对比结果。现场接入在写出配置后上报；已录制的会话可用 `python -m intake.record upload` 补报，不重新调用 LLM。

未配置时不上报任何数据，也不影响运行；Langfuse 侧出错只会产生一条警告。启用后 prompt 和回复会发送到 Langfuse，内容包括数据统计、字段名和决策文字，不含原始数据行。

## 跨任务经验

Memory 根据样本量、特征数、坏样本率、缺失率和时间跨度检索相似的历史任务。距离超过阈值时视为冷启动，不复用历史参数和经验。

LLM 可以提出候选经验，但必须引用真实实验、使用代码允许的经验键，并与实验判定保持一致。经验的验证、启用和废弃由生命周期规则决定。当前检索只依赖上述统计量，无法保证识别所有业务差异。

## 其他运行方式

环境准备、完整数据下载和运行命令见 `RUN.md`。完整数据集不随仓库分发；除演示页外，`examples/` 中也保存了已运行的结果。命令行也可以直接在样本上运行：

```bash
python -m eval.run_task --dataset hotel_bookings --sample --task-id demo --llm mock --full-trials 5 --max-rounds 3
```

测试使用合成数据，运行 `pytest` 即可，不依赖真实数据和网络。接入新数据集前请先阅读 `knowhow/README.md`：部分 YAML 字段只是业务说明，只有代码明确读取的结构化配置才会参与执行。

## 已知边界

尚未实现的功能包括独立 critic 审查、多任务并发 Executor、完整的三级人工门控与异步审批，以及分客群建模。目前已有部分人工等待和恢复入口，但还不是完整的审批系统。

`run_code` 仅使用子进程和超时控制，没有容器级隔离。同一用户权限下的代码仍可能访问宿主机文件或环境变量，不能作为执行不可信代码的沙箱。特征筛选和人工确认也不能替代严格的数据与标签隔离。

现有实验能够说明流程可以跑通、部分设计假设成立，但不足以证明系统在任意数据集上都有效。实际接入业务时，需要逐项确认标签成熟度、字段可得时间、数据切分和验收口径，并检查执行结果是否遵守了这些约定。
