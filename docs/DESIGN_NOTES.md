# 设计取舍与实验发现

这份文档记录几个不是一眼能看出来的设计决定，以及支撑它们的实测数据——包括没有得到支持的假设。判断标准是实验结果，不是希望它成立。

## 1. 跨任务 Memory：价值不是"更快更好"，是"经验不被污染、决策可追溯"

**机制**（`memory/`）：数据集指纹（样本量、特征数、坏样本率、缺失率、时间跨度）→ 固定尺度的欧氏距离检索；超过阈值即**冷启动**，
既不复用 Prior 也不复用 Lesson。Lesson 的生命周期完全由规则决定：LLM 只能**提出**（key 必须是代码从实验树推导的枚举；必须引用真实
`exp_id`；极性必须与证据的判定一致），`CANDIDATE →`（通过最终验收）`VALIDATED →`（≥2 个相似任务复现）`ACTIVE`；出现同 scope 的相反证据 →
`DEPRECATED`。失败经验（NEGATIVE）同样保存。证据只在指纹 scope 匹配时才合并——早期实现里酒店任务的同名经验会被错误地并入 Lending Club
的经验，已修复。

**验证到的**（`eval/memory_demo.py` → `examples/memory_demo.md`）：

| 检查项 | 结果 |
|---|---|
| Lending Club 相邻年份段（指纹距离 0.31） | 检索命中，复用 Prior |
| 酒店（指纹距离 4.98） | 冷启动，不复用任何经验 |
| 5 条经验在第二个相似任务复现 | `CANDIDATE → VALIDATED → ACTIVE` |
| LLM 编造 key / 假证据 / 矛盾极性 / 夹带 `status` 字段 | 全部被丢弃或忽略 |
| 历史任务没有实验通过最终验收 | 不产出 Prior、不晋升任何经验 |

**没有得到支持的假设：用历史最优超参做 warm-start 能加快收敛**。5 个种子下，冷启动与用历史 Prior 起步的 best-so-far AUC 基本持平（在第 3–5 个
trial 甚至略低）：

| 已跑 trial 数 | 1 | 3 | 5 | 10 | 15 |
|---|---|---|---|---|---|
| 冷启动 | 0.6555 | 0.6594 | 0.6603 | 0.6603 | 0.6610 |
| 用历史 Prior | 0.6561 | 0.6571 | 0.6594 | 0.6598 | 0.6608 |

原因：LightGBM 的搜索空间平滑，TPE 在前几个 trial 内就能到达好区域，"历史最优超参做起点"能提供的信息很少。**没有为了让结论好看而调整参数。**

**第二次验证换了角度：结构性经验能否改变真实 LLM 的决策，而不是数值 warm-start 能否加速收敛。** 让 Kimi 从自己两次真实运行的实验树里提出经验
（`race:lgbm` 有效、`race:lr_scorecard` 无效、`tune:lgbm:…@full` 无效等），经规则准入、跨任务复现后晋升 ACTIVE，再让它带着这些经验跑第三次：

| 指标 | 无经验（两次运行行为一致） | 带 ACTIVE 经验 |
|---|---|---|
| 首个被接受的实验出现在第几轮 | 3 | 3 |
| 全保真调参后进入平台期的轮数 | 2 | 1（另 1 轮改为不训练的 INVESTIGATE） |
| 最终 OOT-dev / holdout | 0.6718 / 0.6772 | 0.6718 / 0.6772（相同） |
| token 用量 | 36k / 27k | 49k |

决策确实被改变了，而且有据可查——LLM 的 rationale 逐条引用了经验（"该模型已被历史经验和本轮赛马双重判负，不再投入"）。但最终结果没有变好：
token 反而多了（上下文变长，又被禁忌表拒绝了几次）。原因是这个任务本身上限很低，最优方案第 3 轮就定型了，"少走弯路"没有可兑现的收益。样本量很小
（带经验 1 次、无经验 2 次），只能当案例证据。

一个顺带修复的设计缺陷：Lesson 的 key 起初不含保真度，导致同一组超参在低保真下被判有效、全保真下被判无效，自相矛盾、无法晋升。保真度决定了判定
的含义（低保真最多只能算"有希望"），现在写进 key（`tune:…@low` / `@full`）。

**结论**：Memory 的价值不是让单次搜索更快或更准，而是三件事——① 准入规则让经验不被过拟合结果污染；② 冷启动规则让不相似的任务不被错误经验
误导；③ 决策可追溯（理由能对应到具体历史证据）。在可走弯路更多的任务（比如多表特征挖掘）上，避免重复无效动作也许能转化为效果提升，这一点尚未验证。

## 2. 单调约束：怎么处理"不单调"的边缘情况

**做什么**：告诉 GBDT"这个特征越大，风险只能单调上升或下降，不允许先降后升"。GBDT 是纯数据驱动的，在样本稀疏、有噪声的区间可能学出反直觉的
曲线（比如信用分 720–730 的人比 700–710 的人风险更高）。方向来自 `knowhow/domain_priors.yaml` 的 `risk_direction`，模板产出的特征继承各自的
`monotone_prior`。约束不是免费的：通常损失一点 AUC 换取更稳的跨月表现，所以**不默认生效**，必须经过"加约束 vs 不加约束"的对照实验、且满足
"AUC 不显著变差、分数 PSI 更优"才会保留。

**真实数据里一定存在不单调、甚至先验会出错的特征**，这是这个设计要处理的核心问题：

| 边缘情况 | 例子 | 处理 |
|---|---|---|
| 缺失本身有含义，数值方向不成立 | "距上次逾期的月数"缺失＝从未逾期（风险最低），数值上又是越大越好 | 先验标 0，不加约束 |
| 数值大小含义有两面 | 账户总数——多既可能是信用深，也可能是多头 | 同上，标 0 |
| **先验与实际数据相反** | 模型卡曾发现某字段 SHAP 方向与先验相反 | **数据一致性守卫**：加约束前用 train 上特征与 label 的秩相关检查符号，明显相反就跳过并写进报告，而不是强行扭曲模型 |
| 类别变量 | 押金类型——某类取消率反直觉地高 | 本来就无单调可言，不加约束，交报告标注 |
| 预处理后名字对不上先验 | 原始日期字段被转成"信用历史月数" | 用别名表映射，不改 know-how |
| 缺少先验的新特征 | 模板/`run_code` 产出的新特征 | 有 `monotone_prior` 就继承，没有就不约束；LLM 可以提议方向但必须写业务理由，同样要过对照实验 |
| 模型族不支持 | 线性评分卡 | 该动作对不支持的模型直接校验失败，只在设计里说明单调 WOE 分箱的思路 |

**实测**（Lending Club，lgbm，15 个 trial，`eval/a6_monotone.py` → `examples/monotone_ablation.md`）：

| 配置 | OOT-dev AUC | holdout AUC | 分数 PSI | 与先验方向相反的特征数 |
|---|---|---|---|---|
| 不加约束 | 0.6718 | 0.6772 | 0.0024 | 1 |
| 加约束 | 0.6720 | 0.6781 | 0.0024 | 0 |

AUC 上没有代价（Δ=+0.0002，置信区间跨 0），但这个数据集本来就很稳（PSI 只有 0.002），约束没有可改善的空间，按保留规则判**不保留**。
唯一可见的收益是可解释性（1 个反直觉特征消失了），但这不在当前的保留规则里——要把它纳入需要在评估器里引入 SHAP，暂不做。真实碰到的边缘情况：
某个先验方向为"越大风险越高"的字段，在这批数据上秩相关是负的，数据一致性守卫正确地跳过了这条约束。

一个踩过的坑：第一次运行时"PSI 更优"的判断没有设最小改善幅度，导致 0.0024 对 0.0024（差在第 5 位小数）被当成"更优"而误判为保留——噪声被
当成了收益。现在要求 PSI 改善至少 0.002，并补了回归测试。

## 3. `run_code` 逃生通道：generate 端放开、verify 端收紧的边界案例

**做什么**：LLM 编写 `def compute(df): ...` 形式的 Python 代码，作为特征模板覆盖不到某个假设时的逃生通道，与模板路径共用同一套
`生成 → 筛选 → 训练 → 比较` 流程（`tools/run_code.py`）。

**隔离手段，如实说明取舍**：子进程 + 超时，只挂载单个数据切分的文件，不注入 holdout 路径、也拿不到验收模块的访问令牌。这能防止误用，但不是
操作系统级沙箱——同一用户的子进程理论上仍能用绝对路径读磁盘上的任意文件。真正的强隔离需要容器或 chroot，这里如实说明限制，不假装做到了。

**核心安全规则**：产出无论如何都强制标记为"可得时间不可信"，不管数据集的字段策略如何——因为它绕开了 know-how 里的可得时间标注。必须经人工
批准才能真正用于最终模型。这是"生成端放开、验证端收紧"这条设计主线在这里最重的一处体现。

**写集成测试时意外揭出的两个更早的缺陷**：
1. 特征扩展动作在主循环里从未被真正跑通过——早期的多表特征工厂评估是用独立脚本直接调用底层训练函数，绕开了状态机；状态机的训练步骤一直没有
   把"这次训练要带哪些特征集"这个字段传下去，只是没有测试覆盖到。这次才第一次真正跑通"提议新特征 → 训练"这条路径。
2. 项目数据库里特征集注册表是早期版本建的旧结构，缺新加的一列；建表语句的"不存在则创建"不会给已存在的表加列，补了一次迁移。

## 4. "给基线也加上同样的特征，它就追平了 agent"——这不是负面结果

多表特征挖掘任务上，agent 相对"AutoML + 原始宽表"的 OOT-dev AUC 高出约 0.015、holdout 高出约 0.02，预算翻倍后 AutoML 也没追上。但如果给
AutoML **同样**的、已经过筛选漏斗处理的特征，它就追平了 agent（差值不显著）。这一步容易被误读成"我们的搜索能力不如成熟的 AutoML 库"。

更准确的解读是：**AutoML 本身完全没有泄漏检查和特征构造能力**——它只接收一张现成的特征表，不读 know-how，不知道字段的可得时间，不做
point-in-time 关联，不算单特征 AUC 报警。这些能力全部来自特征工厂（模板 + PIT 规则）和筛选漏斗（含泄漏检查）。"给 AutoML 加同样的特征"这组
对照，本质上是把系统里与搜索无关的另一半（确定性的特征生成 + 泄漏检查代码）已经处理好的成品直接喂给它——不是"AutoML 自己学会了特征工程"。

| 组件 | AutoML 能否独立做到 | 证据 |
|---|---|---|
| 特征工厂（模板 + PIT + know-how） | 不能——没有多表关联能力和领域知识 | 多表任务上 +0.015 的全部增量来自这里 |
| 筛选漏斗（含泄漏检查） | 不能——不认识 know-how | 泄漏注入实验：去掉它，AUC 虚高到 1.0 |
| 超参搜索（Optuna vs FLAML） | 能，这是它的本职 | 两者打平，这本来就不该是卖点 |

所以"加同样特征后打平"是一次干净的分离实验：证明增量 100% 归因于"特征构造 + 泄漏检查"，不是"搜索过程更聪明"——后者本来就该打平，因为
Optuna 和 FLAML 都是成熟的 TPE 实现。真正要论证的从来不是"调参比 AutoML 强"，而是"AutoML 拿不到这些特征，除非先有人（或另一个 agent）替它
把特征工程和泄漏检查做完"。
