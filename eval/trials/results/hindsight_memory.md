# 接手一份新信贷数据时，先从经验中提炼出的检查清单

结合过往处理 home_credit、other_credit、lending_club、hotel_bookings 等数据集的教训，建议按以下优先级检查：

## 1. 识别特殊占位值 / 伪装成数值的缺失
信贷数据常把"缺失"编码成看起来合法的数字，直接当连续变量处理会出错：

- **home_credit `application_train`**：`DAYS_EMPLOYED = 365243` 表示"无工作或已退休"，**不只代表退休人员，也包括失业人员**（该口径经用户修正确认），占样本约 **18%**，且这类客户违约率更低。
- **home_credit `previous_application`**：`DAYS_FIRST_DRAWING` 等 **5 个日期字段**用 `365243` 表示缺失值——需在清洗时识别并单独处理。
- **other_credit**：`-1` 表示该字段未填写（经用户确认）。

> 要点：每个**数据集**的缺失编码约定可能不同（365243 / -1 ...），不要跨表套用同一套规则。

## 2. 检查结果泄漏字段
确认哪些字段是"结果出来之后才产生"的，建模前必须剔除：

- **hotel_bookings `reservation_status`**：属于结果泄漏字段，必须剔除（用户已确认）。

## 3. 明确目标变量的样本口径
违约标签的界定直接决定样本范围：

- **lending_club 违约模型**：只保留已结清（Fully Paid）和已核销（Charged Off）的贷款，**还款中（Current）的贷款不纳入样本**（经用户确认）。

## 4. 评估多表 / 派生特征是否值得
- **home_credit**：若只使用主表，加入派生特征几乎**没有带来性能提升**——提示要先用主表验证基线，再决定是否引入副表与派生特征。

## home_credit 中 DAYS_EMPLOYED 的处理

### 一、这个字段里 365243 到底是什么

根据已记录并经用户确认的信息：

- **在 `application_train` 表中，`DAYS_EMPLOYED = 365243` 是一个特殊取值，表示该客户「没有工作或已退休」，而不是一个真实的就业天数。** 用户进一步补充确认：**它不只代表退休人员，也包括失业人员**，因此不能只按「退休」一种身份去解读。
- **该取值约占样本的 18%**，属于一个规模不小的子群体。
- **这类无业/退休客户的违约率更低。**

从数值本身也能做一点定性推断：365243 天大约是 1000 年，显然不是一个真实可解释的就业时长，所以把它当作连续数值直接喂给模型在语义上是站不住的（这是由数值方向推出的合理估计，并非数据中记录的处理结论）。

### 二、可依据这些事实推出的处理要点

以下是由上述已记录事实推导出的处理思路，属于合理推断，**数据中并没有记录用户对 `DAYS_EMPLOYED` 实际采用的、经确认的具体处理步骤**：

1. **不要把 365243 当作真实天数参与数值运算。** 它与字段中其他真实天数在尺度上不可比，直接保留会让该字段的数值含义失真。
2. **优先考虑「转为缺失 / 占位 + 单独标志」这一类方向。** 即把 365243 替换为一个缺失标记（或在数值列上置为空值），同时用一列哑变量/标志位单独标记「该客户无工作或已退休」。这样做的好处是：
   - 数值列不再被这个异常大值污染；
   - 而「是否无业/退休」这一身份信息因为**与更低的违约率相关**，本身带有预测信号，用标志位保留下来比直接删掉更合理。
3. **不建议直接删除这些样本。** 它们占约 18%，比例不低，且违约率特征与整体不同，删掉会同时损失样本量和一个有区分度的群体特征。
4. **不要让 365243 与 `previous_application` 的缺失标记混淆处理口径。** 已记录的一条（标注为推测、非确认）信息指出：在 `previous_application` 表中，`DAYS_FIRST_DRAWING` 等 5 个日期字段也用 **365243 表示缺失值**。也就是说，365243 在这份数据的两个地方含义不同——在 `application_train.DAYS_EMPLOYED` 里它是一个**有业务含义的特殊状态**（无业/退休），在 `previous_application` 的若干日期字段里它是**缺失值标记**。因此清洗时要按表、按字段分别处理，不能一个规则套全部（该 `previous_application` 的说法本身只是推测，采用前应再核对）。

综合来看，一个与已有事实自洽的做法方向是：**`DAYS_EMPLOYED == 365243` → 数值列置为缺失/占位，并新增一列标志位表示「无工作或已退休」，从而在去除失真数值的同时保留这个与低违约率相关的群体信号。**

**额外看到的好处**：整理结论时，它不会把一个数据集的经验套到另一个上，会提醒「365243 在两张表里含义不同」；没有记录的内容它会明说没有，不会编。这和项目「数字由代码算、大模型不编」的原则是一致的。

**代价**：

- 很重：虚拟环境 1.7 GB，带 PyTorch、transformers、内置 Postgres、litellm。第一次启动要下载并加载向量模型，超过了默认的 30 秒，要把启动等待时间调长。
- 整理结论的回答很长，用在产品里要限制长度（`max_tokens`）或者指定回答格式（`response_schema`）。
- 安装过程第一次卡住了 40 多分钟，重试才成功；放到公司环境前要先确认能不能离线安装。

**决定**：用 Hindsight 存「记录」（使用中学到的经验）。按 PRD，人确认过的业务口径仍然存在项目自己的结构化记录里，不放进 Hindsight。
